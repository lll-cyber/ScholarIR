## 1. 直接回答

### 槽位抽取在子查询分解的**前**还是**后**？

**在前（先槽位 / 理解，后分解与改写）。**

赛题 3.1 的写法本身也是这个顺序：

1. 解析意图 + 多维检索条件（≈ **槽位**）  
2. 子查询分解（≈ **拆成可独立检索的子问题**）  
3. 改写与扩展（≈ **生成更适合引擎的 text**）

逻辑理由：

| 若先分解再抽槽位 | 若先抽槽位再分解 |
|------------------|------------------|
| 各子句各抽一套槽，易冲突、重复 | 全局约束（年份/否定/venue）只抽一次 |
| 否定、时间容易只落在某一个子查询上 | 分解时**带着槽位约束**生成子查询 |
| 难服务 Judge（Judge 需要整句级 criteria） | slots → criteria；sub_queries 只管「搜什么角度」 |

Paper Finder 也是：**先 AnalyzedQuery / criteria，再按类型走检索**，而不是先盲拆子查询。

### 实现上可以「一次 LLM」

为省调用，**允许一次 JSON 同时产出 slots + sub_queries**，但约定：

- Prompt / 思维顺序仍是：**先填 slots，再基于 slots 写 sub_queries**  
- 后处理校验：`sub_queries` 不得违反已填的 `year_*` / `negation`（冲突则改写或丢弃该子查询）

```text
question
  → [逻辑] 槽位抽取（理解）
  → [逻辑] 子查询分解 + 改写扩展
  → UnderstandingResult{slots, criteria, sub_queries}
```

## 2. 冻结的槽位表（v1）

对应赛题用语 → 我们的字段：

| 赛题表述 | 槽位字段 | 级别 | 主要去向 |
|----------|----------|------|----------|
| 核心研究意图 | `intent` | P0 | 路由 / 是否偏 survey |
| 关键实体 / 主题内容 | `topic` | P0 | 写进 sub_query.text；Judge |
| 方法论约束 | `method` | P1 | text + Judge criteria |
| 数据限定 | `data` | P1 | text + Judge（可与 topic 合并若空） |
| 领域限定 | `domain` | P1 | 选源 / text |
| （隐含）时间 | `year_from`, `year_to` | P0 | API filter + Judge |
| （常见）会议/期刊 | `venue` | P1 | 能滤则 API，否则 Judge |
| （常见）作者 | `authors` | P1 | 元数据通路 / Judge |
| （常见）排除条件 | `negation` | P0 | **只给 Judge**，不进 API 硬过滤 |

**v1 不做（P2）**：`modality`、`language`、引用网络约束、必须 survey 的独立布尔（可用 `intent=survey` 表达）等。

### 空值语义（冻结）

- `null` / 缺省 = **未识别**，Retrieval **不得**当成过滤条件。  
- 只有非空槽位才投影到 `SubQuery.filters` 或 API。

### 最小 JSON 示例

```json
{
  "intent": "method",
  "slots": {
    "topic": "federated domain generalization",
    "method": "meta-learning",
    "data": null,
    "domain": "machine learning",
    "venue": null,
    "year_from": null,
    "year_to": null,
    "authors": null,
    "negation": null
  },
  "relevance_criteria": [
    {"name": "topic", "description": "About federated domain generalization", "weight": 0.5},
    {"name": "method", "description": "Uses or studies meta-learning", "weight": 0.5}
  ],
  "sub_queries": [
    {"qid": "q0", "text": "meta-learning federated domain generalization", "channel": "keyword"},
    {"qid": "q1", "text": "federated domain generalization survey", "channel": "keyword"}
  ]
}
```

注意：`sub_queries` 是在 **已有 slots** 上改写/分解出来的，不是另一套无关句子。

## 3. 三步与模块映射（对齐 3.1）

| 赛题 3.1 | 模块内步骤 | 产出 |
|----------|------------|------|
| （1）理解：意图 + 多维条件 | **Step A 槽位抽取** | `intent`, `slots`, 初步 `relevance_criteria` |
| （2）子查询分解 | **Step B 分解** | 多条「子问题」意图（可仍是中间描述） |
| （3）改写与扩展 | **Step C 改写** | `sub_queries[].text`（适合检索引擎的短句/关键词） |

工程上 B+C 可合并为「基于 slots 生成 2～3 条互斥检索式」。

---

## 4. 和「先定槽位」的关系

- **槽位表先冻结（本文 §2）**，再写 Prompt / 代码。  
- 子查询格式已定：源无关 `text` + 可选 `filters`（见上一篇 thread）。  
- 当前 stub 无槽位 → 下一步实现应严格按 **A → B/C** 顺序，即使单次调用。

---

## 5. 组内一句话

> **先槽位、后分解/改写；槽位定全局约束，子查询定检索角度；一次 LLM 可以，但逻辑顺序不能反。**
