## 1. 结论先行（建议冻结）

### 1.1 两层输出，而不是「只吐一种检索式」

```text
自然语言 question
        │
        ▼
┌─────────────────────────────┐
│  A. 结构化中间表示（slots）  │  ← 听懂约束；给 Judge / 过滤 / 路由用
│  B. 通用子查询列表（text）   │  ← 可独立检索的 NL/关键词短句
└─────────────────────────────┘
        │
        ▼  Retrieval 适配层（按源翻译）
   arXiv / S2 / OpenAlex / PubMed 各自 API 参数
```

- **不要**指望一套字符串被所有 API 原样吃下（语法、过滤字段都不通）。  
- **要**先有 **源无关的中间表示**，再在 Retrieval 里做 **per-source 适配**。  
- Understanding 的职责停在 **A + B**；不要在 Understanding 里写死 `openalex.query=...`。

### 1.2 槽位：分层，不一次做全

| 层级 | 槽位 | 理由 |
|------|------|------|
| **P0 必做** | `topic`（主题/内容）、`year_from`/`year_to`（或 recent）、`negation`（不要什么） | 赛题明示；对 F1/过滤影响大；抽错成本可控 |
| **P1 强烈建议** | `method`、`domain`、`venue`、`intent`（survey/找方法/找数据集…）、`authors` | 对应赛题「方法/领域」；Paper Finder / SPAR 都用到 |
| **P2 后置** | `dataset`、`task`、`modality`、`language`、`must_be_survey`、引用关系约束… | 提升上限，但 LLM 抽错会伤 Precision；等主表 F1 稳定再加 |

原则：**槽位为空 = 未知，不是「无约束」**；没抽到就别硬过滤。

### 1.3 效率平衡

- Understanding **一次 LLM 调用**尽量吐出：intent + P0/P1 slots + 2～3 条 `sub_queries`（可 JSON）。  
- 不要为每个槽位单独调一次模型。  
- 检索式条数默认 **2～3**，上限 5（对齐 SPAR `QUERY_NUM_PRUNED` / PaSa `search_queries`）。  
- 复杂槽位（否定、venue）优先进 **Judge 的 relevance_criteria**，不一定全部变成 API filter（API 常不支持「否定」）。

## 2. 槽位清单（建议 schema）

与 `UnderstandingResult.slots` / `SubQuery.filters` 对齐：

```text
slots:
  topic: str | null           # 核心研究对象内容
  method: str | null          # 方法/架构约束
  data: str | null            # 数据/场景限定（P2 可并入 topic）
  domain: str | null          # 领域：NLP / CV / bio …
  venue: str | list | null    # ACL / NeurIPS …
  year_from: int | null
  year_to: int | null
  authors: list[str] | null
  negation: list[str] | null  # 排除条件（给 Judge，少给 API）
  intent: str | null          # survey | method | dataset | specific_paper | broad …

relevance_criteria:           # 给 Judge 的子条件（可从 slots 展开）
  - {name, description, weight}

sub_queries:                  # 给 Retrieval 的可检索单元
  - {qid, text, channel, filters?}
```

**`text` 是什么：**  
源无关的 **短检索语句或关键词串**（英文优先，学术库更友好），例如：

- `"low-resource named entity recognition survey"`  
- `"hybrid architecture reconstruction-based anomaly detection"`  

**不是** Google 布尔式全家桶，也不是某家 API 的 DSL。

## 3. 各基线怎么做（对照）

| 系统 | 有没有槽位 | 输出给检索的是什么 | 多源怎么办 |
|------|------------|-------------------|------------|
| **PaSa** | 基本无 | 多条互斥 NL 检索式 → Google `site:arxiv.org` | 单路径，不抽槽 |
| **SPAR** | **轻量**：intent / domain / time / suitable_sources | 先扩 NL 检索式；对 OA/S2 再 **按源抽 keywords** | **适配在检索侧**：源感知关键词 |
| **Paper Finder** | **最全**：content / authors / venues / time / broad·specific + **RelevanceCriteria** | 很少「多条通用检索式」；按 `query_type` **路由整条流水线** | 槽位驱动 Dense/S2/元数据等不同通路 |
| **PaperQA2** | 几乎无 | Agent 临场写本地 keyword + year | 本地索引，无关开放 API |

要点：

- 赛题 3.1 写的「理解 + 分解 + 改写」= **规格上限**；基线没有谁三条都满分。  
- **槽位最像赛题的是 Paper Finder**；**多源检索式最像可落地工程的是 SPAR**。  
- 我们建议：**槽位学 PF（精简版）+ 子查询/多源适配学 SPAR**。

## 4. 「通用检索式」vs「各 API 专用」——讨论结论

### 4.1 各 API 并不兼容同一查询串

| 源 | 典型输入 | 过滤能力 |
|----|----------|----------|
| Serper→arXiv | 自然语言 / 关键词 + `before:date` | 时间可拼进 query；venue 弱 |
| Semantic Scholar | query 字符串 + year 等参数 | 年份 API 友好 |
| OpenAlex | 关键词 / filter 语法 | venue、概念需 filter，不是纯 NL |
| PubMed | 布尔式 / MeSH 风格 | 与 CS 顶会 query 差异大 |

因此：**Understanding 输出「通用 text + slots」→ Retrieval 再翻译**，例如：

```text
SubQuery.text = "retrieval augmented generation question answering"
slots.year_from = 2020

→ arxiv/serper:  "retrieval augmented generation question answering before:2020-01-01" 或 end_date 参数
→ semantic:      query=text, year="2020-"
→ openalex:      search=text, filter=from_publication_date:2020-01-01
```

### 4.2 推荐数据流（冻结）

```text
Understanding
  → slots（结构化）
  → sub_queries[].text（通用、源无关）
  → sub_queries[].filters（可选，从 slots 投影：year/venue…）

Retrieval.adapt(source, sub_query, slots)
  → 该源的 API 调用参数
```

**反对**：Understanding 直接生成 `openalex_filter=...`（换源就要改 Understanding）。  
**反对**：只有 slots、没有 `text`（语义检索/Google 仍需要可搜字符串）。  
**反对**：只有一条原始 NL、完全无 slots（否定/venue 进不了 Judge，赛题 3.1 也难写满）。

## 5. 全面 vs 效率：实操建议

| 策略 | 做法 |
|------|------|
| 调用次数 | Understanding **1 次** LLM → JSON（slots + criteria + sub_queries） |
| 槽位宽度 | v1 只强制填 P0；P1 能填则填，填不稳就 null |
| 子查询数 | 默认 2～3；互斥覆盖优于同义堆砌 |
| 否定/复杂逻辑 | 进 `relevance_criteria` / Judge，不强行 API filter |
| 失败兜底 | JSON 解析失败 → stub：原句 1 条 subquery（与当前 stub 兼容） |
| 评测意识 | AutoScholar 金标偏短；槽位过滤过猛会伤 Recall——filter 宜松、Judge 宜紧 |

## 6. 与当前代码的差距

| 项 | 现状（`understanding/base.py`） | 目标 |
|----|-------------------------------|------|
| slots | `{}` | P0/P1 抽取 |
| sub_queries | 原句 1 条 | 2～3 条改写/分解 |
| criteria | 整句 overall | 可由 slots 展开 |
| LLM | 无 | `vendor_spar.local_request` + `instruction` 模板 |
| API 适配 | 无（Retrieval stub） | `retrieval` 内 per-source adapt |

## 8. 一句话对齐

> **Understanding = 结构化槽位（听懂）+ 少量通用子查询（搜得到）；**  
> **Retrieval = 按源翻译，不要求 API 兼容同一种字符串；**  
> **Judge = 消化否定与细条件，保护集合 F1。**

组员若只改一处：先实现「一次 LLM → JSON slots(P0/P1) + 2～3 条 text」，Retrieval 适配可以第二步再做。
